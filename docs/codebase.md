# 100.AI.TrainData 代码库文档

## 项目架构

100.AI.TrainData项目采用了基于规则的数据生成架构，主要分为三个部分：

1. **规则定义**（rules/）：以文本形式定义各种业务场景的规则
2. **数据模型**（src/entity/）：以JSON结构化形式表示规则和数据要素
3. **服务层**（src/service/）：实现数据生成和处理的服务类

## 核心组件详解

### 1. 规则文件（rules/）

规则文件是整个系统的基础，它们定义了各种业务场景下数据生成的模式。每个规则文件具有相似的结构：

```
/开发 本地训练数据生成服务

在本地生成数据
一，[业务对象]数据要素
01.要素1
02.要素2
...

二、要素组合规则
...

[三、要素组合要求]
...

四、举例
...

五，问题解析的格式
...
```

#### 人员管理规则（staff/）

**searchStaff**：
- 定义查询项目人员的规则
- 包含3个基本要素：项目未安排人员查询、人员被安排项目查询、项目人员查询
- 规定了回答格式，包括操作、对象、人员等信息

**updateStaff**：
- 定义更新项目人员的规则
- 包含9个基本要素：添加项目人员、人员信息、项目信息、角色信息等
- 规定了人员撤销和添加的操作格式

#### 成本管理规则（cost/）

**searchCargo**：
- 定义查询货单的复杂规则
- 包含24个基本要素：查询动作、货单信息、项目、供应商、状态等
- 支持按照提交时间、审核时间、发货时间等多种条件查询

**updateCargo**：
- 定义更新货单的规则
- 包含6个基本要素：操作类型、供应商、项目、发货单号、送货单号等
- 支持两种主要规则：操作+供应商+项目+发货单号、操作+供应商+项目+送货单号
- 其他支持的操作包括审核通过货单、导出结算单、审核退回货单、删除货单等

#### 订单管理规则（po/）

**searchPo**：
- 定义查询订单的复杂规则
- 包含23个基本要素：查询动作、订单信息、项目、供应商、状态等
- 支持按照金额范围、材料类型、工程属性等多种条件查询

#### 合同管理规则（contract/）

**searchContract**：
- 定义查询合同的复杂规则
- 包含17个基本要素：查询动作、合同信息、项目、供应商、状态等
- 支持按照调价规则、工程属性、材料工艺图等多种条件查询

### 2. 数据模型（src/entity/）

#### 基础数据要素（baseElements/）

每个业务场景对应一个JSON文件，结构化地表示规则文件中定义的数据要素：

```json
{
  "businessObject": "searchStaff",
  "baseDataList": [
    {
      "name": "查询",
      "number": "01",
      "conditionList": ["有哪些项目还没安排人员"],
      "originalText": "有哪些项目还没安排人员？",
      "originalLogic": "查询项目没有安排人员",
      "originalRegex": ".*项目.*没.*安排.*人员.*"
    },
    ...
  ]
}
```

这些文件将文本规则转换为结构化的数据模型，便于程序处理和理解。

#### 回答要素（answerElements/）

定义了针对各种业务场景问题的回答格式：

```json
{
  "answerObject": "searchStaff",
  "answerElements": [
    {
      "name": "operation",
      "nameCN": "操作",
      "relateToBase": "无",
      "isStatic": "是",
      "staticValue": "查询"
    },
    {
      "name": "project",
      "nameCN": "项目",
      "relateToBase": "03",
      "isStatic": "否"
    },
    ...
  ]
}
```

这些文件定义了问题应该如何回答，包括哪些字段是静态的，哪些需要动态关联到基础数据要素。

#### 关系定义（relationship/）

该目录用于定义业务实体间的关系，目前尚未实现。未来可以定义如：
- 人员与项目的多对多关系
- 合同与订单的一对多关系
- 订单与货单的一对多关系

#### 千问服务（QwenService）

`QwenService`是一个独立的服务，用于将生成的数据转换为通义千问模型所需的训练格式。它不继承自`BaseGenerationService`，而是通过调用其他服务来获取数据，然后进行格式转换。

主要功能包括：
- 问题数据格式化为自然语言
- 答案数据转换为JSON字符串
- 构建千问格式的训练数据
- 将数据保存为JSONL文件

通义千问格式的训练数据示例：
```json
{
  "messages": [
    {
      "role": "user",
      "content": "### 指令：\n你是一个企业信息检索助手，请根据查询内容，返回包含以下字段的标准JSON响应，缺失字段填\"无\"：\n[操作, 对象, ...]\n\n### 查询问题\n删除人员，工号041501的从重庆江北国际机场临空经济区工程项目的钢材负责人角色"
    },
    {
      "role": "assistant",
      "content": "{\"操作\": \"删除人员，\", \"对象\": \"人员安排\", ...}"
    }
  ]
}
```

使用方式：
```python

```

## 数据生成流程

基于当前的项目结构，完整的数据生成流程是：

1. **规则解析**：解析文本形式的规则文件，提取数据要素和组合规则
2. **模型转换**：将解析结果转换为JSON结构的基础数据要素
3. **服务调用**：使用相应的服务类（如StaffingService或StaffUpdateService）生成数据
4. **数据格式化**：将生成的数据转换为所需的格式（如通义千问格式）

## 技术实现细节

### 基础数据要素格式

基础数据要素是对规则文件中定义的要素的结构化表示，主要包含：

- **name**：要素的语义名称
- **number**：要素编号，用于在规则中引用
- **conditionList**：要素的变体列表，表示同一语义可能的不同表达方式
- **originalText**：原始文本描述
- **originalLogic**：逻辑说明
- **originalRegex**：匹配该要素的正则表达式

### 回答要素格式

回答要素定义了如何构建回答，主要包含：

- **name**：要素名称
- **nameCN**：中文名称
- **relateToBase**：与基础数据要素的关联，可能是：
  - "无"：表示没有关联
  - 数字（如"03"）：关联到特定编号的基础要素
  - 组合（如"05,07|07,15"）：表示与多个基础要素的复杂关联
- **isStatic**："是"或"否"，表示是否为静态值
- **staticValue**：如果是静态值，则提供具体内容

### 数据生成规则

从规则文件中可以总结出以下数据生成规则：

1. **基本要素组合**：基本要素可以按照定义的规则组合成完整的问题
2. **变体生成**：每个基本要素可能有多个变体表示，系统应随机选择变体
3. **上下文约束**：某些要素的使用受到其他要素的约束
4. **回答映射**：问题中的要素需要映射到相应的回答格式中

## 代码扩展指南

要扩展当前的代码库，可以考虑以下几个方向：

### 添加新的业务场景

1. 在rules/目录下创建新的规则文件
2. 将规则转换为src/entity/baseElements/中的JSON文件
3. 定义对应的回答要素格式，保存到src/entity/answerElements/

### 增强现有功能

1. 完善relationship/目录，定义业务实体间的关系
2. 开发数据生成工具，自动化训练数据生成流程
3. 实现规则验证机制，确保规则的一致性和有效性

### 开发辅助工具

1. 规则编辑器：可视化编辑规则文件
2. 数据预览器：预览生成的训练数据
3. 规则转换器：自动将文本规则转换为JSON结构

## 最佳实践

在使用和扩展本项目时，建议遵循以下最佳实践：

1. **保持一致性**：新添加的规则和要素应与现有格式保持一致
2. **文档化**：为新添加的规则和要素提供详细的文档说明
3. **版本控制**：使用git等版本控制工具管理规则和模型的变更
4. **测试验证**：为生成的数据建立验证机制，确保质量
5. **模块化**：将功能实现为独立的模块，便于维护和扩展
