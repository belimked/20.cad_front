## 1. Goals and Background Context

### 1.1 Goals（目标）

- **简化 CAD 到 PDF 的转换流程**：提供一站式桌面应用，用户无需在多个工具间切换即可完成 CAD 文件上传、转换和预览
- **异步处理与实时反馈**：采用异步任务模型，用户提交任务后立即获得任务序号，通过实时进度监控了解处理状态
- **批量处理能力**：支持一次性上传和处理多个 CAD 文件，提高工作效率
- **清晰的文件关系可视化**：通过图形化连线展示 CAD 原文件与生成 PDF 的对应关系，避免文件混淆
- **便捷的结果预览与下载**：集成 PDF 在线预览功能，支持单个或批量下载转换结果
- **跨平台桌面体验**：基于 Tauri 框架，提供轻量级、高性能的原生桌面应用

### 1.2 Background Context（背景上下文）

CAD 文件（如 DWG 和 DXF 格式）转换为 PDF 是工程设计领域的高频需求。设计人员需要将 CAD 图纸转换为 PDF 格式以便与客户、项目团队分享和评审，或满足归档和合规要求。然而，现有的转换工具通常存在以下问题：需要在线等待处理完成、无法直观追踪多个文件的处理状态、转换后的文件与原文件难以对应匹配。

本项目旨在构建一个统一的桌面应用程序，通过异步任务处理模型解决上述痛点。应用将与后端 API 深度集成：用户上传 CAD 文件后立即获得任务序号，应用持续监控任务状态并绘制实时进度条；处理完成后自动调用 PDF 生成接口，并通过可视化连线图展示原文件与生成文件的对应关系。基于 Tauri 框架，应用具备接近原生性能的跨平台能力和较小的体积，为用户提供流畅的本地桌面体验。

### 1.3 典型用户场景示例

**场景：CAD 文件转 PDF 处理流程**

**用户角色**：工程设计人员

**场景描述**：
李工程师需要将手头的 CAD 设计图转换为 PDF 格式，以便与客户和项目团队分享评审。他打开 CAD 文件处理应用，完成了以下流程：

#### 详细步骤流程：

1. **启动应用**
   - 李工程师双击桌面图标，启动 CAD 文件处理应用
   - 应用快速加载，显示简洁的主界面

2. **选择并上传 CAD 文件**
   - 点击"选择文件"按钮或直接拖拽 DWG 文件到上传区域
   - 应用显示选中文件信息（文件名、大小、格式）

3. **提交处理任务（API 异步通信）**
   - 点击"开始处理"按钮
   - 应用调用后端 API，将文件上传并创建异步处理任务
   - API 立即返回任务序号（Task ID），无需等待处理完成

4. **实时任务监控**
   - 应用使用任务序号持续轮询后端 API 获取处理状态
   - 任务列表显示当前状态：
     - 排队中 (Queued)
     - 处理中 (Processing)
     - 已完成 (Completed)
     - 失败 (Failed)

5. **进度可视化**
   - 显示动态进度条（0-100%）
   - 实时更新百分比数值

6. **完成通知**
   - 当检测到任务状态变为"已完成"时
   - 应用自动调用"CAD 生成 PDF 接口"
   - 获取生成的 PDF 文件下载链接

7. **文件关系展示**
   - 应用显示 CAD 原文件与生成的 PDF 文件的对应关系
   - 使用可视化连线图展示文件映射关系：
     ```
     源文件.dwg ────→ 生成文件.pdf
     ```
   - API 提供数据（文件 ID、文件名、下载 URL 等）
   - 应用负责绘制连线和布局展示

8. **结果操作**
   - 点击 PDF 文件可在线预览
   - 点击下载按钮获取文件

## 2. Requirements

### 2.1 Functional Requirements（功能性需求）

#### 文件上传与管理：

- **FR1**: 应用应支持通过文件选择对话框选择单个 CAD 文件（仅支持 DWG 格式）
  - **验收标准**：文件选择对话框仅显示 .dwg 扩展名文件；选择非 DWG 文件时显示错误提示

- **FR2**: 应用应支持拖拽方式上传单个 DWG 文件到指定区域
  - **验收标准**：拖拽 DWG 文件到上传区域后，文件信息立即显示；拖拽非 DWG 文件时显示"仅支持 DWG 格式"提示

- **FR3**: 应用应在上传前显示选中的文件信息，包括文件名、大小和格式
  - **验收标准**：文件选中后，界面显示完整文件名、文件大小（以 MB 为单位，保留 2 位小数）、格式标识（DWG）

- **FR4**: 应用应允许用户在提交前取消选中的文件
  - **验收标准**：点击"取消"或"清除"按钮后，文件信息清空，上传区域恢复初始状态

#### 异步任务处理：

- **FR5**: 应用应调用后端 API 上传 DWG 文件并创建异步处理任务
  - **验收标准**：点击"开始处理"后，应用发送 POST 请求到后端 API，请求包含文件数据；API 响应时间超过 5 秒时显示"上传中"提示

- **FR6**: 应用应在任务创建后立即接收并存储任务序号（Task ID）
  - **验收标准**：API 返回任务序号后，应用在任务列表中显示该序号；任务序号应唯一且持久化存储（应用重启后仍可查看）

- **FR7**: 应用应处理 API 调用失败情况，向用户显示错误信息并提供重试选项
  - **验收标准**：API 返回 4xx/5xx 错误时，显示具体错误信息（如"上传失败：网络超时"）；提供"重试"按钮，点击后重新调用 API

#### 任务状态监控：

- **FR8**: 应用应使用任务序号持续轮询后端 API 获取任务处理状态
  - **验收标准**：任务创建后，应用每 3 秒调用一次状态查询 API；轮询在任务完成或失败后停止

- **FR9**: 应用应显示每个任务的当前状态（排队中、处理中、已完成、失败）
  - **验收标准**：任务列表中每个任务显示清晰的状态标签；状态变更时标签和颜色实时更新（排队-灰色、处理-蓝色、完成-绿色、失败-红色）

- **FR10**: 应用应为每个处理中的任务显示实时进度条（0-100%）
  - **验收标准**：任务状态为"处理中"时显示进度条；进度条百分比与 API 返回的进度值一致；进度条平滑更新，无跳跃或闪烁

- **FR11**: 应用应在任务状态变更时更新 UI（无需用户手动刷新）
  - **验收标准**：状态从"排队中"变为"处理中"时，UI 在 3 秒内自动更新；无需用户点击任何刷新按钮

#### PDF 生成与下载：

- **FR12**: 应用应在检测到任务完成后，自动调用后端"CAD 生成 PDF"接口
  - **验收标准**：任务状态变为"已完成"后，应用在 2 秒内自动调用 PDF 生成接口；调用失败时显示错误提示

- **FR13**: 应用应获取并存储生成的 PDF 文件下载链接
  - **验收标准**：PDF 生成接口返回下载链接后，应用存储该链接并在 UI 中显示"下载 PDF"按钮

- **FR14**: 应用应支持单个 PDF 文件下载
  - **验收标准**：点击"下载 PDF"按钮后，弹出文件保存对话框；用户选择保存位置后，文件成功下载到本地；下载进度实时显示

#### 文件关系可视化：

- **FR15**: 应用应通过图形化方式展示 CAD 原文件与生成 PDF 的对应关系
  - **验收标准**：任务完成后，界面显示两个文件卡片（CAD 和 PDF）；两个卡片之间有明显的连线或箭头指示映射关系

- **FR16**: 应用应使用连线或其他可视化元素表示文件映射关系（例如：源文件.dwg ──→ 生成文件.pdf）
  - **验收标准**：连线样式清晰可见（建议实线、箭头）；鼠标悬停在连线上时高亮显示相关的两个文件

- **FR17**: 应用应从后端 API 获取文件关系数据（文件 ID、文件名、下载 URL）
  - **验收标准**：API 返回的数据包含必需字段（原文件名、PDF 文件名、PDF 下载 URL）；应用正确解析并显示这些信息

#### PDF 在线预览：

- **FR18**: 应用应集成 PDF 查看器组件
  - **验收标准**：应用内嵌 PDF 渲染引擎（如 pdf.js 或系统原生组件）；PDF 文件加载成功后显示第一页内容

- **FR19**: 应用应支持点击已完成的 PDF 文件进行在线预览
  - **验收标准**：点击 PDF 文件卡片或"预览"按钮后，在应用内打开 PDF 查看器；PDF 内容在 3 秒内加载完成

- **FR20**: PDF 查看器应支持基本操作：缩放、旋转、翻页
  - **验收标准**：提供缩放按钮（放大/缩小）或滚轮缩放；提供旋转按钮（顺时针/逆时针 90°）；提供翻页按钮（上一页/下一页）或键盘方向键翻页

- **FR21**: PDF 查看器应支持多页 PDF 的页面跳转和缩略图导航
  - **验收标准**：显示当前页码和总页数（如"第 3 页 / 共 10 页"）；提供页码输入框，输入页码后跳转到指定页；侧边栏显示所有页面的缩略图，点击缩略图跳转到对应页

#### 任务管理：

- **FR22**: 应用应保留任务历史记录，用户可查看过去的处理任务
  - **验收标准**：应用启动后显示历史任务列表（至少保留最近 50 条）；每条记录显示任务序号、原文件名、处理时间、状态

- **FR23**: 应用应支持清除已完成或失败的任务记录
  - **验收标准**：提供"清除历史"按钮；点击后弹出确认对话框；确认后清除所有非"处理中"状态的任务记录

### 2.2 Non-Functional Requirements（非功能性需求）

#### 性能：

- **NFR1**: 应用启动时间应在 3 秒以内
  - **验收标准**：从双击应用图标到主界面完全显示的时间不超过 3 秒（在标准硬件配置下测试）

- **NFR2**: 文件上传进度应实时反馈，无明显延迟
  - **验收标准**：文件上传过程中，进度条更新频率至少每秒 1 次；上传完成后，进度条在 0.5 秒内显示 100%

- **NFR3**: 任务状态轮询频率应合理（建议 3 秒间隔），避免过度请求后端 API
  - **验收标准**：监控网络请求日志，确认状态查询 API 调用间隔为 3±0.5 秒；任务完成后立即停止轮询

#### 可靠性：

- **NFR4**: 应用应处理网络异常情况（如断网、超时），向用户提供友好的错误提示
  - **验收标准**：模拟断网场景，应用显示"网络连接失败，请检查网络"提示；网络恢复后，应用自动恢复轮询或提示用户重试

- **NFR5**: 应用应在任务轮询失败时自动重试，最多重试 3 次后提示用户
  - **验收标准**：API 调用失败后，应用在后台自动重试（间隔 5 秒）；重试 3 次仍失败后，显示错误提示并停止轮询

- **NFR6**: 应用应在异常退出后能够恢复正在监控的任务状态
  - **验收标准**：强制关闭应用后重新启动，正在处理的任务仍显示在任务列表中；应用自动恢复轮询，继续监控任务状态

#### 用户体验：

- **NFR7**: 应用 UI 应简洁直观，核心操作流程不超过 3 步
  - **验收标准**：从启动应用到查看 PDF 预览，总操作步数不超过 3 步（选择文件 → 开始处理 → 预览 PDF）

- **NFR8**: 应用应为所有异步操作提供加载指示器或进度反馈
  - **验收标准**：所有网络请求（上传、轮询、下载）期间显示加载动画或进度指示；操作完成后加载指示器立即消失

- **NFR9**: 应用应在操作失败时提供明确的错误信息和建议的解决方案
  - **验收标准**：错误提示包含具体原因（如"文件格式不支持"）和建议操作（如"请选择 DWG 文件"）；避免技术性错误代码（如"Error 500"）

#### 兼容性：

- **NFR10**: 应用应支持 Windows 10/11、macOS 11+、主流 Linux 发行版
  - **验收标准**：在上述每个平台上成功构建和运行应用；核心功能（上传、监控、预览、下载）在所有平台上正常工作

- **NFR11**: 应用应仅支持 DWG 格式的文件上传
  - **验收标准**：上传 DXF 或其他格式文件时，显示"仅支持 DWG 格式"错误提示；文件选择对话框仅显示 .dwg 文件

#### 可维护性：

- **NFR12**: 应用代码应遵循 Tauri 最佳实践和前端框架的编码规范
  - **验收标准**：代码通过 ESLint/Clippy 静态检查；代码结构清晰，模块职责单一；关键函数有注释说明

- **NFR13**: 应用应包含完善的错误日志记录机制，便于问题排查
  - **验收标准**：所有 API 调用失败、异常情况记录到日志文件；日志包含时间戳、错误类型、上下文信息；日志文件存储在用户可访问的位置

- **NFR14**: 应用应支持配置化的 API 端点地址，便于切换环境（开发、测试、生产）
  - **验收标准**：API 端点地址存储在配置文件中（非硬编码）；提供环境切换机制（如配置文件或环境变量）；切换环境后无需重新编译应用

## 3. User Interface Design Goals

### 3.1 Overall UX Vision（整体用户体验愿景）

应用应提供**简洁、高效、专注**的桌面体验。用户界面围绕核心工作流程设计（上传 → 监控 → 预览 → 下载），避免不必要的导航和复杂操作。整体风格应专业、现代，符合工程类软件的审美习惯。

**关键体验原则**：
- **任务导向**：界面布局突出当前任务状态，用户始终清楚"我在做什么"和"下一步是什么"
- **实时反馈**：所有异步操作（上传、处理、下载）提供即时的视觉反馈
- **减少认知负担**：单任务模式，用户专注于当前处理的文件，无需管理复杂的任务队列
- **操作可逆**：关键操作（如清除历史）提供确认提示，避免误操作

### 3.2 Key Interaction Paradigms（关键交互范式）

1. **拖拽式文件上传**
   - 主界面中央提供明显的拖拽上传区域
   - 视觉反馈：拖拽文件悬停时区域高亮，松开鼠标后立即显示文件信息

2. **自动状态转换**
   - 任务状态自动流转，无需用户手动触发
   - 状态变更时使用动画过渡，提供连贯的视觉体验

3. **可视化文件关系**
   - 使用卡片 + 连线的方式展示 CAD → PDF 的映射关系
   - 连线应带有方向性（箭头），清晰表达转换关系

4. **内嵌 PDF 预览**
   - 点击 PDF 文件后，在应用内打开预览面板（非外部浏览器）
   - 预览面板提供关闭按钮，快速返回主界面

5. **进度可视化**
   - 使用进度条 + 百分比文字的组合
   - 不同状态使用不同颜色编码（灰色-排队、蓝色-处理中、绿色-完成、红色-失败）

### 3.3 Core Screens and Views（核心屏幕和视图）

从产品角度，以下是实现 PRD 价值和目标的关键屏幕：

1. **主界面 - 文件上传与任务监控**
   - 上传区域（拖拽或点击选择文件）
   - 当前任务状态卡片（显示文件名、状态、进度）
   - 文件关系可视化区域（CAD ──→ PDF 连线图）
   - 操作按钮（开始处理、下载 PDF、预览 PDF、清除历史）

2. **PDF 预览窗口**
   - PDF 内容渲染区域（支持缩放、翻页、旋转）
   - 工具栏（缩放按钮、旋转按钮、翻页按钮、关闭按钮）
   - 页码指示器（当前页 / 总页数）
   - 缩略图侧边栏（可选，用于多页 PDF 快速导航）

3. **历史任务列表**（可选独立视图或主界面一部分）
   - 历史任务记录列表
   - 每条记录显示：任务序号、文件名、处理时间、状态
   - 操作按钮（查看详情、清除历史）

### 3.4 Accessibility: None

基于项目的工程软件性质和 MVP 阶段，暂不考虑 WCAG 级别的无障碍要求。

**基本无障碍考虑**（作为良好实践）：
- 使用足够的颜色对比度（文字与背景）
- 为按钮和交互元素提供清晰的视觉反馈（悬停、点击状态）
- 确保关键操作可通过键盘完成（Tab 键导航、Enter 确认）

### 3.5 Branding（品牌风格）

**假设风格方向**（基于工程类桌面应用的常见审美）：

- **色调**：中性色为主（灰色、白色、深蓝色），辅以状态色（蓝色-进行中、绿色-成功、红色-失败）
- **字体**：现代无衬线字体（如 Inter、Roboto、思源黑体），清晰易读
- **图标**：简洁的线性图标风格（与 Tauri 应用常见风格一致）
- **布局**：卡片式设计，清晰的内容分组和视觉层次

### 3.6 Target Device and Platforms: Desktop Only

**目标平台**：桌面应用（Windows、macOS、Linux）

**屏幕尺寸考虑**：
- 最小窗口尺寸：1024 x 768 像素
- 推荐窗口尺寸：1280 x 800 像素或更大

## 4. Technical Assumptions

### 4.1 Repository Structure: Monorepo

**决策**：使用 **Monorepo（单一代码仓库）** 结构

**理由**：
- 项目由前端（TypeScript/框架）和 Tauri 后端（Rust）组成，两者紧密耦合
- Tauri 标准项目结构本身就是 Monorepo 形式（`src/` 存放前端代码，`src-tauri/` 存放 Rust 代码）
- 便于版本管理和同步发布
- 单一 Git 仓库简化了开发流程

**结构示例**：
```
.
├── src/                    # 前端源码
│   ├── components/         # UI 组件
│   ├── services/          # API 调用服务
│   ├── stores/            # 状态管理
│   └── utils/             # 工具函数
├── src-tauri/             # Tauri 后端（Rust）
│   ├── src/               # Rust 源码
│   │   ├── main.rs
│   │   └── commands.rs    # Tauri 命令
│   └── tauri.conf.json    # Tauri 配置
├── public/                # 静态资源
└── docs/                  # 项目文档
```

### 4.2 Service Architecture

**决策**：**桌面前端应用 + 远程 HTTP API**

**架构说明**：
- **桌面应用层**（Tauri）：
  - 前端 UI（TypeScript + 前端框架）
  - Rust 后端（处理本地文件操作、系统集成）

- **远程 API 层**（不在本项目范围内）：
  - 后端 API 服务（提供 CAD 处理、PDF 生成、任务管理接口）
  - 本项目仅作为 API 的客户端

**通信方式**：
- 前端 ↔ Tauri Rust 后端：通过 Tauri Commands（IPC）
- Tauri Rust 后端 ↔ 远程 API：通过 HTTP/HTTPS（使用 `reqwest` crate）

**关键决策**：
- 文件上传由 Rust 后端处理（利用 Rust 的高性能文件 I/O）
- 状态轮询由前端 JavaScript/TypeScript 处理（利用 `setInterval` 或 `setTimeout`）
- 本地任务状态存储使用 Tauri 的持久化存储（如 `tauri-plugin-store`）

### 4.3 Testing Requirements
